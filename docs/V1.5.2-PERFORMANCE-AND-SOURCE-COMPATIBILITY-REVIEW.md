# Free New Desk V1.5.2 性能与来源兼容性优化评估报告

- 基线仓库：`the private Free New Desk repository`
- 基线分支：`main`
- 基线版本：`1.5.2`（根目录及桌面端 `package.json`）
- 基线提交：`85d277bb651b7abe14021e93a467cf46c7cecdad`
- 评估日期：2026-11-06
- 状态：**评估方案初稿；代码逐文件审计、性能实测和实施验收尚未完成**
- 工作分支：`codex/v152-performance-source-compat`

## 1. 执行摘要

本报告以 V1.5.2 的 `main` 分支为唯一基线，目标是解决用户反馈的界面卡顿、操作响应迟缓、页面跳转缺少连贯动效，以及影视源协议覆盖不足问题。

总体建议：保留 Electron + Vue 3 + TypeScript + Pinia + Vite、独立 C++ PlayerHost/libmpv、Source Engine、JVM SpiderHost、Drpy2 Worker、Plugin Host 的现有分层，不进行推倒重写。先建立性能基线，再按证据优化渲染、IPC、数据访问、来源加载和播放器生命周期。

用户提出的“流畅度提升一倍、响应时间减少 50%”作为验收目标，而非当前已实现结论。没有相同硬件、相同数据集、相同场景、相同构建模式的前后测量，不得宣称达标。

来源兼容方面，建议形成统一 Spider 能力契约，按运行时隔离 JavaScript、Drpy、Python、普通 JVM JAR，并将依赖 Android API 的 DEX/WebView/JNI 源交给 Android Companion 或明确标记不支持。禁止为了兼容率而在 Electron 主进程内执行不可信源代码。

## 3. 性能问题诊断计划

目前没有可用的 V1.5.2 同机性能基线，不能把任何具体函数或模块断言为已确认根因。按以下链路逐层采样：

1. Renderer：主线程长任务、Vue 组件更新次数、布局/绘制、图片解码、DOM 节点数量、内存与 GC。
2. Router：页面挂载/卸载耗时、路由守卫、数据预取、状态恢复、重复初始化。
3. IPC：调用排队时间、序列化体积、主进程 handler 耗时、往返 P50/P95/P99。
4. Data Service：SQLite 查询计划、索引命中、事务锁等待、N+1 查询、重复读写。
5. Source Engine：来源并发度、DNS/连接/首字节/解析耗时、失败超时、重试风暴、取消传播。
6. PlayerHost：进程启动、Pipe 建连、HWND 创建/挂接/几何同步、媒体打开、首帧、缓冲和销毁。
7. 系统资源：CPU、GPU、磁盘 I/O、工作集、句柄数、线程数及长时间运行泄漏。

### 3.1 基准测试场景

至少建立以下固定场景，并记录硬件、Windows 版本、电源模式、显示缩放、窗口尺寸、网络条件、缓存冷热状态和数据集摘要：

- 冷启动至首页可交互。
- 热启动至首页可交互。
- 首页切换点播/直播/搜索/收藏/历史。
- 进入分类、翻页、筛选、搜索、详情。
- 直播列表加载和 EPG 展示。
- 多来源并发搜索（固定来源数与响应 fixture）。
- 播放器启动、暂停、Seek、切换线路、关闭和再次进入。
- 连续 50 次页面跳转及至少 30 分钟稳定性运行。

### 3.2 性能指标与目标

| 指标 | 测量方法 | 目标 |
|---|---|---|
| 页面切换 | 用户操作到目标页面可交互，P50/P95/P99 | P95 ≤ 基线 50% |
| IPC 往返 | 带 requestId 的端到端计时，分操作类型 | P95 ≤ 基线 50% |
| 首屏可交互 | 冷/热启动分开测量 | P95 ≤ 基线 50% |
| 列表滚动 | 帧时间、掉帧率、长任务 | 常见场景稳定接近 60 FPS |
| 来源首批结果 | 首次可见有效结果时间 | P95 至少降低 50% |
| 播放器控制 | 控制请求受理与实际状态变化分别计时 | P95 至少降低 50% |
| 内存与稳定性 | 工作集、GC、句柄、崩溃/泄漏 | 不以性能优化引入回归 |

“流畅度提升一倍”需定义为可复现的操作吞吐/帧时间/掉帧率组合指标。建议主要验收使用固定脚本每分钟完成的有效交互数及 P95 帧时间，不可把主观评分直接换算成 2 倍。

## 4. 性能优化建议

### 4.1 Renderer 与 Vue

- 用 Vue Devtools/性能标记确认高频更新组件，减少不必要的深层响应式对象。
- 大型来源、频道、影片列表使用虚拟滚动或分页，不一次性渲染全部项目。
- 海报使用尺寸分级缩略图、解码优先级、并发限制和有界 LRU 缓存；避免原图批量解码。
- 对列表项使用稳定 key，避免筛选、排序后大范围重建。
- 高频播放状态使用细粒度订阅，避免全局状态每秒刷新导致页面树重渲染。
- 先显示缓存/骨架与首批结果，再后台补齐；明确加载、空结果、失败和部分成功状态。
- 组件卸载时取消请求、释放订阅和观察器，防止离页任务继续更新 UI。

### 4.2 IPC 与进程边界

- 对高频状态采用事件推送或批量快照，减少定时轮询；设置节流/合并策略。
- 大数据传输避免重复 JSON 深拷贝；只传必要字段，限制单次 payload。
- 保留 requestId、超时、取消、代次/epoch 和 owner 校验，避免过期响应覆盖新页面或新播放器会话。
- 任何优化不得放宽 Named Pipe ACL、Bearer Token、当前用户身份检查或单实例锁。
- 对可能耗时的网络、解析、文件、媒体操作保持异步，不在 Renderer/Main UI 线程同步等待。

### 4.3 数据与来源加载

- 检查 SQLite 慢查询并依据实际查询计划增补索引；索引变更必须测量写入成本。
- 为首页、分类、详情、搜索建立明确缓存键、TTL、容量上限、失效策略和来源版本隔离。
- 多来源请求采用可配置并发池、单来源超时、总超时、取消传播、熔断/退避；禁止无界 Promise.all。
- 先返回首批成功结果，慢源后台补充；单源失败不阻塞整个页面。
- 缓存必须区分来源身份、参数、页码、过滤器和配置版本，避免串源数据。
- 网络请求、重定向、Header、Cookie 和代理继续经统一 Broker 与来源权限策略。

### 4.4 PlayerHost

- 先用现有性能指标定位启动、媒体打开、窗口几何同步或状态轮询哪个阶段占时。
- 在严格单所有者、epoch 和资源释放约束下复用 PlayerHost 会话；不要盲目常驻或复用失效 HWND。
- 将媒体加载与 UI 控制解耦，播放器忙时仍能查询状态、停止和处理窗口生命周期。
- 对几何同步做变化检测、合并和节流；不要发送重复的无效窗口更新。
- 首帧时间、音视频缓冲、硬解状态和解码错误分开记录。
- 保留真实媒体测试与 Windows DPI/多屏/高对比度验收。

## 5. SmartTube 风格导航和动效

参考 SmartTube 的交互理念：方向键焦点明确、焦点移动连续、内容优先、导航层级稳定、加载反馈即时。只借鉴交互原则和可观察行为，不复制其品牌资产或未经许可的代码。

建议动效规范：

| 场景 | 建议时长 | 实现原则 |
|---|---:|---|
| 主路由切换 | 160–200ms | opacity + translateX，小幅位移 |
| 详情页进入 | 180–240ms | 背景/详情分层过渡 |
| 卡片焦点 | 100–140ms | transform + outline/box-shadow |
| 侧栏展开 | 160–200ms | transform/opacity |
| 弹窗 | 140–180ms | opacity + scale |
| 播放器 OSD | 120–180ms | translateY + opacity |

要求：
- 优先动画 transform/opacity，避免动画 width/height/top/left 等引起布局抖动。
- 使用统一 Vue transition/transition-group 与全局 token，不在各页面散落不一致 CSS。
- 支持 prefers-reduced-motion；低性能设备可关闭非必要背景动画。
- 路由切换期间保留明确焦点目标，返回后恢复原列表滚动位置和选中项。
- 动效不能延迟用户输入响应；页面数据加载与过渡动画并行，不能等网络请求结束才开始动画。
- 自动化 UI 测试检查焦点、键盘/遥控器操作、动画结束状态和重复导航，不只检查截图。

## 6. 来源协议与运行时兼容架构

### 6.1 统一能力契约

统一 Source/Spider Adapter API，标准化：

- initialize(ext/config)
- homeContent
- homeVideoContent
- categoryContent
- detailContent
- searchContent
- playerContent
- destroy / cancel
- request / storage / log / proxy capability

返回值标准化为统一 VOD、Live、Search、Detail、PlayResult DTO。保留原始来源类型、错误阶段、耗时、能力声明和兼容状态，避免将协议“能解析”误报为“能播放”。

### 6.2 运行时矩阵

| 类型 | Windows 执行策略 | 兼容等级建议 |
|---|---|---|
| CMS XML/JSON | 原生适配器 | P0 |
| TVBox/FongMi 配置 | 统一配置解析及适配器 | P0 |
| M3U/TXT/JSON Live | 原生解析 | P0 |
| XMLTV/EPG | 现有解析器增强 | P0 |
| Drpy2 | 现有独立 Worker | P0 |
| Drpy1 | 独立兼容 Worker/适配层 | P1 |
| QuickJS/JS Spider | 固定版本 JS Runtime Worker | P1 |
| Python Spider | 独立 CPython Worker | P1 |
| 纯 JVM JAR | 现有 JVM SpiderHost | P1 |
| Android DEX/JNI/WebView | Android Companion 或明确不支持 | P2 |

### 6.3 Python Spider

建议新增独立 Python Worker，而非在 Electron 主进程嵌入解释器：

- 固定受支持的 Python 版本与依赖策略。
- 采用 JSON-RPC/stdin-stdout 或受认证本地 IPC，协议有版本号和消息大小限制。
- 每个源独立进程或受控 Worker 池；设置 CPU、内存、执行时间、并发、输出体积和网络预算。
- 通过宿主提供受控 request/storage/log API，不默认暴露任意文件系统和任意网络。
- 兼容常见 Spider 生命周期与 ext 初始化，但需逐个样本验证具体 API、返回结构和 Python 包依赖。
- 依赖锁定、哈希、来源代码审核、授权快照；代码或依赖变化后重新授权。
- Python 预览不等于沙箱；Windows Job Object/低权限账户/AppContainer 等 OS 隔离需另行验证。仅用子进程、虚拟环境或 Python VM 不得宣称安全沙箱。
- 明确标注需要 Android API、原生二进制或特定 Linux 包的 Python 源不兼容。

### 6.4 Android Spider

建议先做 Android Companion 可行性原型，而不是承诺 Windows 直接运行 DEX：

- Companion 在用户可控 Android 设备/模拟器运行，暴露版本化、认证的 RPC。
- Windows 侧负责来源配置、统一结果 DTO、播放和 UI。
- Companion 侧执行 Android Context、DexClassLoader、WebView/JNI 等 Android 专属能力。
- RPC 只回传结构化结果、播放 URL、必要 Header/DRM 能力声明；敏感凭据不得写日志。
- 连接必须显式配对、认证、可撤销；限制远程调用范围和频率。
- Android Companion 不等于所有源都可播放：DRM、设备绑定、登录态、硬件解码和系统 WebView 行为都可能限制跨设备播放。
- Companion 断开时明确显示“需要 Android 运行时/设备离线”，不伪报源无效。

## 7. 安全、许可和供应链

- 继承 V1.5.2 已有的来源代码审核、授权摘要、权限检查、超时与网络预算。
- 不可信 Spider 不得进入 Electron Renderer 或 Main。
- 插件/Spider 的 VM 隔离不等于 OS 沙箱；对任意代码执行应采用独立低权限进程和系统级隔离。
- 运行时下载必须固定版本、校验哈希、签名/来源、许可证和更新策略。
- Python 包、JAR、Android 组件、QuickJS、mpv/FFmpeg 的许可证分别审查；不得将依赖生态的许可证等同于本项目许可。
- 对用户来源地址、Cookie、Token、播放 URL 和本地文件路径做日志脱敏。
- Android Companion 网络入口不得默认监听公网；优先用户明确配对的局域网连接或 USB/ADB 开发连接。

## 9. 验收矩阵

### 性能
- 固定硬件、系统、分辨率、DPI、电源模式和数据集。
- 冷/热启动、页面跳转、列表、搜索、详情、直播、播放等场景均测 P50/P95/P99。
- 性能优化前后同一脚本、同一环境、同一构建模式。
- 页面切换/IPC/首屏主要响应 P95 降低至少 50%。
- 代表性交互吞吐提升至少 2 倍或帧时间/掉帧指标达到预先定义的等价目标。
- 连续 50 次跳转和 30 分钟压力测试无明显内存/句柄增长、无过期响应覆盖。

### 兼容
- 配置解析、首页、分类、详情、搜索、播放解析分别统计通过率。
- 至少覆盖 CMS、TVBox、FongMi、Drpy1/2、Python、纯 JVM JAR、直播列表和 EPG。
- 每个样本记录来源版本、配置摘要、运行时版本、能力状态、请求耗时和失败阶段。
- Android 专属样本分别在 Companion 上测试；不能将 Windows 不支持的 API 算作 Windows 完全兼容。

### 工程与安全
- Linux verify 和 Windows x64 原生构建、测试、打包门禁通过。
- Named Pipe/IPC 权限、单实例、取消、超时、来源授权和日志脱敏回归通过。
- 安装、升级、回退、卸载及用户数据保留验证。
- 依赖许可证与运行时供应链审查完成。
- 重要测试失败不得通过删除断言、放宽门槛或伪造 fixture 规避。

### 12.2 首轮性能风险线索：重复播放器状态轮询

已读取 `App.vue`、`HomeShellView.vue`、`PlayerView.vue` 和 `stores/playback-clock.ts`，发现不同 UI 层存在重叠的播放器状态轮询：

- App 根布局约每 1500ms 查询一次 stats；
- HomeShell 首页约每 1500ms 再查询一次 stats；
- PlayerView 约每 1000ms 并发查询 stats、tracks、load-status 和 runtimeSession；
- playback-clock 约每 275ms 并发查询 stats、load-status 和 runtimeSession，并通过 requestAnimationFrame 在两次样本间插值显示进度。

这些调用不一定全部在同一页面同时运行，但 Player 页面上根布局、播放器页和播放时钟的查询确实重叠；首页上 App 与 HomeShell 也重复读取 stats。这是**已确认的冗余 IPC 负载线索**，尚不是经 CPU/IPC trace 证明的唯一卡顿根因。

建议下一阶段以播放会话事件 + 单一共享快照/时钟为中心，按字段需求复用样本，减少相同 stats/runtime 的重复查询。需要保留 freshness、sampleSeq、hostEpoch、requestId、loadId 和 controlRevision 检查；不能为了减少 IPC 而使用过期状态或放宽播放器会话校验。

## 14. V1.5.5 Python Spider 兼容性增量

本分支已在既有默认关闭的 T3_PY 可信预览中增加独立编写的轻量 `requests` API 兼容层：

- 支持 `import requests`、`requests.get/post/request`、`requests.Session` 的 GET/POST、默认/自定义 headers、简单字典 cookies、params、form/JSON POST。
- 提供常见响应字段：status_code、ok、headers、url、encoding、content、text、json()、raise_for_status()。
- 支持 `requests.exceptions` 子模块导入的 RequestException、HTTPError、Timeout、ConnectionError 基础异常名。
- 所有调用复用现有 urllib 辅助实现的 HTTP(S)、TLS 验证、超时、4 MiB 响应上限、重定向跨源凭据剥离和禁用环境代理策略。
- 该实现不是第三方 requests 包，不支持连接池、完整 CookieJar、requests.adapters、multipart、stream、PUT/DELETE、auth、代理适配器等高级 API；lxml/bs4/crypto 等 pip 依赖仍不支持。
- Python 运行仍默认关闭且仅限用户主动审核批准的可信代码预览；这项 API 兼容没有增加 OS 沙箱或 RequestBroker 网络强制隔离，也不代表可以安全执行任意互联网 Python 源。

新增真实本地 HTTP fixture 集成测试覆盖模块导入、GET params、POST JSON、Session headers/cookies 和异常子模块。该测试在 Windows/Linux Actions 通过前仍为待验证。应用版本同步推进到 1.5.5。

## 15. Android 来源兼容结论（再次明确）

Android Companion 当前代码是 loopback + AndroidKeyStore TLS 的内置音频 fixture，且明确没有外部 JAR/DEX loader、WebView、JNI、HLS 或 SourceAdapter 注册。桌面端 Android runtime plan 会在 JVM 启动前对 A2–A4 需求 fail-closed。

这意味着当前已经完成 Android 运行时识别和传输安全原型，但尚未实现通用 Android Spider 执行。后续要支持外部 Android 源，必须先设计独立低权限执行服务、代码/依赖摘要授权、OS 级隔离、请求权限 Broker、设备配对和真实设备负向测试。仅把外部 DEX/JAR 交给 Companion 进程加载，会把整个设备应用进程暴露给任意代码，不可接受。
